# 2026-08-13 Codex 图片渲染兼容模式交接文档

> 对应人工验收文档：[Codex 图片渲染兼容模式人工测试文档](../qa/2026-08-13-Codex图片渲染兼容模式-人工测试文档.md)

## 背景

2026-07-16 的实现只负责给新建第三方 Codex Provider 补齐
`x-openai-actor-authorization`，使 Codex 能显示内置 `image_gen` 工具。它没有解决以下问题：

- Codex 内置 Images API 请求没有独立代理路由。
- 图片请求会落入文本模型映射、参数注入或媒体改写链路。
- 大型图片编辑请求与 Base64 响应存在内存、日志和渲染风险。
- Provider 原始 `/v1`、`env_key` 与图片专用 `/coding` 上游需要隔离。
- Codex Desktop 原生图片卡片空白时，没有安全的本地文件渲染兜底。
- 图片兼容自动接管与用户手动接管之间缺少明确的所有权状态。

本次新增“Codex 图片渲染兼容模式”，把 Images API、本地路由、私密 Key
派生、受管 Skill、个性化配置、接管状态机和设置页状态展示整合成一个闭环。

## 用户侧效果

设置 → 通用 → Codex 应用增强中新增：

**Codex 图片渲染兼容模式**

- 默认开启，旧设置文件缺少该字段时也默认开启。
- 当前 Provider 必须是精确的 Tuzi `/v1` 或 `/coding` HTTPS 线路。
- Provider 原始 URL、`env_key`、模板和界面输入保持不变。
- 图片请求内部固定使用 `gpt-image-2`，转发到
  `https://api.tu-zi.com/coding`。
- 接管期间 live `config.toml` 临时指向本地代理；关闭接管后恢复。
- 设置页只显示 Provider URL、`env_key`、私密派生 Key 名、图片上游、
  模型和就绪原因，不显示 API Key 明文。
- Codex 原生图片预览空白时，受管 Skill 可把当前会话里的图片安全发布为
  PNG、JPEG 或 WebP 本地预览。

## 配置关系

### 原 Provider 配置

原配置继续保持以下形态，不强制改成 `/coding`：

```toml
model_provider = "tuzi"

[model_providers.tuzi]
base_url = "https://api.tu-zi.com/v1"
env_key = "TUZI_CODEX_API_KEY"
wire_api = "responses"
requires_openai_auth = false
http_headers = { "x-openai-actor-authorization" = "http://coding.tu-zi.com" }
```

兼容层只接受：

- `https://api.tu-zi.com/v1`
- `https://api.tu-zi.com/v1/`
- `https://api.tu-zi.com/coding`
- `https://api.tu-zi.com/coding/`

协议、主机、端口、路径、查询参数或 fragment 不符合要求时，不派生图片 Key，
也不自动启用图片路由。

### 私密图片 Key

图片专用 Key 名固定为：

```text
TUZI_CODEX_IMAGE_API_KEY
```

派生优先级：

1. Provider `auth.OPENAI_API_KEY`
2. Tuzi Switch 受管环境文件中，Provider `env_key` 对应的值
3. 受信任变量名白名单中的进程环境变量

允许直接读取的进程环境变量名：

- `OPENAI_API_KEY`
- `TUZI_CODEX_API_KEY`
- `CODING_CODEX_API_KEY`
- `TUZI01_CODEX_API_KEY`

任意导入配置即使使用合法 Tuzi URL，也不能通过 `env_key` 读取
`AWS_SECRET_ACCESS_KEY` 等无关进程机密。

派生结果只写入 Tuzi Switch 自己的受管 `codex-env` 文件，不修改系统环境变量。

### live 接管配置

接管期间，当前 Provider 的 live 配置会：

- 把 `base_url` 临时指向本地 `http://127.0.0.1:<port>/v1` 或 IPv6 回环地址。
- 保留 `wire_api = "responses"`。
- 写入进程级随机请求头 `x-tuzi-image-token`。
- 使用 `PROXY_MANAGED` 本地代理占位凭据。

当前进程 Token、live 代理地址或接管占位符不匹配时，旧 live 配置不会被误判为
可复用，接管会重建。

普通文本请求转发到上游前会剥离 `x-tuzi-image-token`，避免泄露图片路由凭据。

## Images API 路由

生成与编辑共注册 8 条入口：

```text
/images/generations
/v1/images/generations
/v1/v1/images/generations
/codex/v1/images/generations

/images/edits
/v1/images/edits
/v1/v1/images/edits
/codex/v1/images/edits
```

所有入口会归一化到固定上游：

```text
https://api.tu-zi.com/coding/images/generations
https://api.tu-zi.com/coding/images/edits
```

查询参数原样保留。

## 图片请求处理

### generation

- 只接受 `application/json`。
- 请求体最大 4 MiB。
- 支持受限解压，解压后仍受 4 MiB 限制。
- 请求总上传超时 30 秒，分块空闲超时 10 秒。
- 只接受 `model = "gpt-image-2"`。
- 校验后继续转发原始 JSON 字节，不重新序列化、不注入文本模型参数。

### edit

- 只接受未压缩的 `multipart/form-data`。
- 请求体最大 64 MiB。
- 上传总超时 5 分钟，分块空闲超时 30 秒。
- 上传内容以 64 KiB 分块流式写入临时文件。
- multipart boundary、preamble、header、字段数和文本字段均有上限。
- 只提取并验证 `model = "gpt-image-2"`，不重建 multipart。
- 上游请求继续从临时文件流式读取，不把完整编辑请求载入内存。

### response

- 上游响应使用流式透传。
- 不缓存完整图片响应。
- 不把完整图片 Base64 写入日志。
- 客户端中途断开或上游流未完整结束时，代理状态记录为失败。

### 并发与退避

- 图片请求最大并发数为 4。
- 并发槽耗尽时返回 `429` 和 `Retry-After: 1`。
- 图片 HTTP Client 使用连接池，但禁用自动重定向和自动重试。

## 单次提交与故障转移边界

图片 POST 明确采用 **at-most-once** 策略：

```text
redirect = none
retry = never
send_once = 一次提交
```

原因：请求超时、连接中断或收到 5xx 时，客户端无法确认上游是否已经完成生图和计费。
自动换 Key 或 Provider 重放同一个 POST 可能造成重复生图和重复计费。

因此当前版本：

- 不跟随 `307` / `308` 重放 POST。
- 不对连接失败、超时、429 或 5xx 自动重放。
- 不宣称支持“同一次图片请求透明故障转移”。
- 普通文本模型的既有故障转移逻辑保持不变。

如果未来上游提供跨节点生效的幂等键或任务查询协议，才可安全扩展图片同请求故障转移。

## 本地访问保护

Images API 同时校验：

1. TCP 来源必须是 loopback。
2. `Authorization` 必须是 `Bearer PROXY_MANAGED`。
3. `x-tuzi-image-token` 必须匹配当前进程随机 Token。
4. Token 使用常量时间比较。
5. 带 `Origin` 或 `Sec-Fetch-*` 的浏览器来源请求被拒绝。

兼容模式只支持：

- `127.0.0.1`
- `::1`
- `localhost`
- `0.0.0.0`，客户端实际使用 `127.0.0.1`
- `::`，客户端实际使用 `::1`

指定 LAN 地址监听时不会报告图片兼容已就绪，也不会自动接管。

## 受管文件与权限

### 私密写入

以下文件使用临时文件、flush、`sync_all` 和同目录原子替换：

- Codex live `config.toml`
- Tuzi Switch 受管 `codex-env`
- 图片兼容 ownership 状态
- 受管 Skill 文件
- 受管 `AGENTS.md` / `AGENTS.override.md`

Unix 下新文件强制使用 `0600`。

### 受管 Skill

内置 Skill：

```text
codex-image-render-fallback
```

包含：

- `SKILL.md`
- `agents/openai.yaml`
- `scripts/extract_images.py`
- `.tuzi-switch-managed`

安全策略：

- 已存在且不属于 Tuzi Switch 的同名 Skill 不覆盖。
- 拒绝 Skill 目录和受管子路径中的符号链接。
- 卸载时只删除内容仍与内置版本一致的受管文件。
- 用户修改的文件和额外文件保留，并释放 ownership。
- 新安装中途失败时清理本轮写入的文件。

### 个性化配置

兼容模式在有效的全局指令文件中写入受管区块：

```md
<!-- TUZI_SWITCH_CODEX_IMAGE_COMPAT_START -->
只要是生成图片相关的需求，都使用 API Key 中内置的 gpt-image-2 生成，接口地址使用 https://api.tu-zi.com/v1。
<!-- TUZI_SWITCH_CODEX_IMAGE_COMPAT_END -->
```

选择规则：

- 非空 `AGENTS.override.md` 优先。
- 否则使用 `AGENTS.md`。
- 只维护带完整起止标记的受管区块。
- 标记损坏、重复或出现在行内时拒绝覆盖。
- Prompt 保存、导入和回填时不会把该受管区块写入用户 Prompt 数据。

## 接管所有权状态机

状态文件记录：

- `activating`：图片兼容正在自动开启接管。
- `owned`：当前接管由图片兼容自动开启。
- `manual_disabled`：用户明确手动关闭了 Codex 接管。

行为：

- 图片条件就绪且 Codex 未接管时，兼容层自动开启接管。
- 用户手动关闭后，即使 Provider 变更，也不会自动夺回。
- 用户手动开启时，接管所有权转交用户。
- 关闭图片兼容开关会清除 `manual_disabled`。
- 再次开启图片兼容开关后，允许自动接管。
- 代理接管期间切换 Codex Provider 时，先同步新的受管 Key，再更新代理目标和恢复备份。
- 图片条件失效时，只关闭由图片兼容自己拥有的接管，不关闭用户主动开启的接管。

## 就绪状态

设置页通过只读命令读取状态，不触发文件写入或代理启停。

可能的状态原因：

| reason | 含义 |
| --- | --- |
| `disabled` | 图片兼容开关已关闭 |
| `no_provider` | 未选择 Codex Provider |
| `unsupported_provider` | 当前 Provider 不是受支持的 Tuzi `/v1` 或 `/coding` |
| `provider_config_invalid` | Provider TOML 无效 |
| `missing_credential` | 没有可用的私密派生 Key |
| `managed_credential_unreadable` | 受管 Key 文件无法读取 |
| `managed_files_missing` | Skill 或个性化受管区块不完整 |
| `local_route_inactive` | 本地代理、live 地址或当前进程 Token 未生效 |
| `ready` | 图片兼容链路完整就绪 |

`ready` 必须同时满足：

- Provider 合法。
- 私密 Key 可读。
- 受管 Skill 文件完整。
- 个性化受管区块完整。
- Codex 路由已开启且代理运行。
- live `base_url` 指向当前代理。
- live 图片 Token 匹配当前进程。

## Codex 配置目录切换

设置中的 Codex 配置目录发生变化时：

1. 清理旧目录中属于 Tuzi Switch 的 Skill 和个性化区块。
2. 在新目录重新收敛图片兼容文件。
3. 任一步失败时清理新目录残留。
4. 回滚应用设置。
5. 恢复旧目录的兼容状态。

不会整目录删除用户文件。

## 同步与 Provider 生命周期接入

以下操作后会重新收敛图片兼容状态：

- 新增、更新、切换或同步 Codex Provider。
- 代理接管中的 Codex Provider 热切换。
- 配置导入。
- WebDAV 下载。
- 设置保存与 Codex 配置目录切换。
- 应用启动后的运行态恢复。

Provider 热切换中：

- 同步路径先更新受管 Key，避免切换瞬间继续使用旧 Key。
- 运行态调度随后检查接管所有权、live 地址和 Token。

两步职责不同，不应合并为一次无条件异步调度。
