# 版本历程功能交接文档

## 功能背景

应用顶部导航栏新增「版本历程」入口，用于在应用内集中展示项目自首次正式发布至当前最新版本的完整变更记录。

版本档案以 [tuziapi/tuzi-switch](https://github.com/tuziapi/tuzi-switch) 的正式语义化 Git Tag、Tag 提交、相邻版本代码差异、GitHub Release 和 `CHANGELOG.md` 为依据，不使用未经验证的推测内容。

## 用户侧功能

顶部导航栏的时钟图标为常驻入口。点击后打开版本历程弹窗，提供：

- 当前安装版本、最新正式版本与收录数量。
- 全部正式版本的发布日期和变更数量。
- 按版本独立展开或收起详情。
- 按版本号、功能或问题关键词搜索。
- 按变更类型筛选。
- 一键重置搜索和筛选条件。
- 跳转对应 GitHub Release。
- 检测到新版本时显示状态标记。

版本标题仅显示版本号，不设置产品阶段或产品代际等人为分类。

## 版本收录范围

当前收录全部 52 个正式语义化版本：

- `v3.12.4–v3.12.19`
- `v1.0.0–v1.0.2`
- `v1.1.0–v1.1.31`
- `v1.2.0`

不收录：

- `main` 等非语义化标签。
- 未创建正式 Tag 的开发提交。
- 临时测试版本。
- 无事实来源的版本描述。

版本按照 Tag 所指提交的日期倒序排列。52 个版本的版本号、完整提交哈希和日期均已与本地同步后的远程 Tag 精确核对。

## 变更分类

| 分类 | 定义 |
| --- | --- |

| 功能增强 | 既有能力的扩展、交互完善或覆盖范围提升。 |

## 代码实现

### 顶部入口

`src/App.tsx` 在设置按钮之后接入 `VersionHistory`，不改变现有检查更新入口的职责。

### 版本历程组件

`src/components/version-history/VersionHistory.tsx` 负责：

- 顶部入口和新版状态标记。
- 弹窗打开与关闭状态。
- 当前安装版本读取。
- 搜索、分类筛选和筛选重置。
- 多版本展开状态保持。
- 当前版本与最新版本标识。
- GitHub Release 安全外部跳转。
- 小窗口响应式布局。

该功能保持为单一聚合组件，避免为简单交互增加不必要的组件层级。

### 版本档案

`src/data/versionHistory.ts` 保存结构化静态档案：

```ts
interface ProductRelease {
  version: string;
  publishedAt: string;
  commit: string;
  releaseUrl: string;
  changes: ReleaseChange[];
}
```

版本档案随前端资源发布，不在用户打开弹窗时请求 GitHub API，因此支持离线查看且不受外部接口限流影响。

### 国际化

版本历程界面文本已加入：

- `src/i18n/locales/zh.json`
- `src/i18n/locales/en.json`
- `src/i18n/locales/ja.json`

版本变更正文以中文专业术语维护；界面操作文本支持中文、英文和日文。

## 展开与筛选规则

- 首次打开优先展开当前安装版本；未匹配时展开最新版本。
- 同一时间允许展开多个版本。
- 搜索或切换分类不会重置已展开版本。
- 版本号命中时保留该版本；正文命中时只显示符合条件的变更。
- 分类筛选仅显示包含对应类别变更的版本。
- 存在搜索或分类条件时显示「重置筛选」。

## 性能与安全边界

- 不新增后端服务或运行时 Git 历史扫描。
- 不在弹窗打开时请求远程版本数据。
- 版本详情仅在展开后进入可见区域。
- 长列表使用滚动容器，不扩展应用窗口高度。
- 不渲染 GitHub Release HTML。
- 外部链接复用现有 `settingsApi.openExternal`。
- 不建立持续增长的缓存或全局事件监听器。
- 异步读取应用版本时使用有效状态标记，组件卸载后不更新状态。

## 自动化校验

`src/data/versionHistory.test.ts` 校验：

- 版本号不重复。
- 版本号符合正式语义化 Tag 格式。
- 发布日期符合 ISO 日期格式。
- Commit 为完整 40 位 SHA。
- Release URL 与版本号一致。
- 每个版本至少包含一条有效变更。
- 版本按照发布日期倒序排列。

## 后续维护流程

发布新版本时：

1. 在 `src/data/versionHistory.ts` 首部追加新版本记录。
2. 以正式 Tag、提交差异和 Release Notes 核定变更内容。
3. 保留完整 Commit SHA 和对应 Release URL。
4. 执行版本档案测试、类型检查和前端构建。
5. 确认当前应用版本可以在档案中匹配。

不得仅复制提交标题作为用户可见说明；应在不改变事实含义的前提下转写为规范的产品发布术语。
