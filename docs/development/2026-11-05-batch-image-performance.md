# UC-PERF-01：批量生图期间的界面刷新

2026-11-05。用户明确反馈是生成中拖动画布和输入不顺，已选择「局部刷新进度，保留批量数量与现有并发」。本轮基于正式 main `e6020c53b7589a6c7f92a9066e3ea313a72f6c25`，分支 `codex/opentu-batch-interaction-performance`，仅本地修复、验证和提交，不自动替换已发布安装包。

## 定位与改动

1. 桌面 SVG 占位通过展示计时器和画布状态两条路径刷新，每次均 `replaceChildren()` 重建背景、网格、动画及文字。现在保留相同结构的节点，只有进度条宽度、描述或无障碍标签实际变化时才修改。阶段、位置/尺寸、批次数量、预览及错误详情变化仍重新绘制；失败状态的重试、关闭与复制保持原语义。
2. 画布同步计时器把预计进度写回画布节点，引发画板保存和外围刷新。展示控制器已有独立进度时钟，现在仅预计进度/字幕变化时不把画布标为脏；真实任务事件、任务绑定、阶段、结果及几何恢复仍正常同步保存。后台任务本身的持久化未改，重新打开时从任务开始时间恢复预计进度。

不修改批量选择、提交并发、模型请求、任务队列、真实结果保存、原有供应商或付费行为。没有新增数据库/账户/配置字段、数据迁移或运行依赖。

## 性能证据

使用真实本地画布、工作流、任务队列、原生 SVG 分支与 IndexedDB；仅 HTTP 边界替换为合成响应，外网阻断。生成请求暂停期间测量，再释放结果核对数量与重载。每组独立浏览器存储。记录见 [性能 JSON](evidence/2026-11-05-batch-performance.json)。

| 合成 Chrome 场景 | 修复前 | 修复后 |
|---|---:|---:|
| 正常速度，20 张，8 秒占位整树重建 | 300 | 0 |
| 6 倍 CPU 降速，20 张，8 秒整树重建 | 283 | 0 |
| 同场景静止等待 4 秒，画布保存 | 3 | 0 |

以上是单次合成对比，CPU 降速不是实际低配机器。常速强机器空画布没有复现明显停顿，20 张降速场景的帧间隔也没有显著改善；不能据节点/保存次数下降宣称所有用户卡顿已解决。没有测试反馈用户的设备、真实大项目或大图内存压力，没有调用付费模型。

## UC-PERF-01.2：继续减少等待阶段的重复计算

用户在首轮提交 `653708a9` 后要求继续优化。沿用已批准的局部刷新方案，批量数量、并发、请求行为与真实任务持久化不变，本轮没有新增持久化字段或依赖。

- 一次同步扫描内共用任务列表快照；下次事件/定时器仍重新读取，空扫描不读取历史。20 个占位的任务列表读取从每轮 20 次降为 1 次；额外加入 1000 条无关历史任务验证绑定和最新失败状态。不是跨事件缓存，避免读到过期任务。
- 展示时钟只有整数百分比变化时才请求 React 刷新，到预计上限后停止。对单个已达上限的占位，60 秒内计时器引起的渲染从 60 次降为 0 次；更换开始时间（重试）、预计时长或进入图片加载阶段仍更新，卸载清理定时器。
- 匹配历史任务时直接检查主任务 ID 和小型绑定列表，避免对每个候选任务重新构造相同 Set；工作流及批次槽匹配条件不变。

新增前两项回归先在旧代码复现失败（读取 20 次、渲染 60 次），修改后通过。20 张 Chrome 和 WebKit 均验证输入完整、手形拖拽实际位移、无额外占位重建/静止画布保存、恰好 20 次请求、20 个结果保存及重载，无页面错误。普通 Chrome 帧间隔 P95 约 16.8 ms，WebKit 约 18 ms；没有据此宣称用户卡顿已彻底消失。结构化记录见 [第二轮证据](evidence/2026-11-05-batch-performance-round2.json)。

本轮创作全量 132 文件 / 2154 项、类型检查、完整 renderer 构建通过；来源补丁 1565 文件逐字节还原、OpenSpec strict 和非生成 patch 的差异空白检查通过。构建保留既有大分块提示。仍仅本地，未推送/合并/更新公开安装包。
