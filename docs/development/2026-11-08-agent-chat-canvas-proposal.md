本轮用户明确提出：聊天生成的图片同步到画布；复用现有 Agent，支持流式正文和思考过程；画布底部主输入框与侧边聊天协同；先看具体方案和关键页面。本文替代 UC-TEXT-05 中仅双向回填文字的建议，原方案保留为历史记录。

## 1. 建议结论

采用“一个创作会话、两个输入入口、一套 Agent 与任务队列”。侧边聊天是完整的交互与结果记录；底部输入框是当前画布的快捷操作入口。两者共享提交后的上下文与任务，输入中的草稿分别保存，不逐字互相覆盖。

这比只做“提示词复制”更符合本轮需求。旧创作助手界面仍隐藏；复用其背后的 Agent、工具注册、模型路由和任务执行能力，不恢复旧界面。

| 方案 | 优势、适用场景 | 缺点、维护成本和风险 |
| --- | --- | --- |
| A：两套聊天分别工作，只传提示词/图片 | 改动较少，适合先做简单互传 | 历史断开，“继续改这张图”难关联；易重复生成；短期成本低、长期同步维护成本高 |
| B：共享会话与任务，保留两个输入入口（推荐） | 连续对话、生成和改图可追溯，聊天与画布引用同一结果 | 必须统一任务归属、事件和恢复机制；初期成本中等偏高，后续只维护一套执行链 |
| C：恢复旧创作助手并直接换皮 | 可短期复用旧工作流消息展示 | 会带回刚隐藏的复杂界面；旧流式标签/单活动工作流引用不足以安全支撑多会话，后续返工风险高 |

推荐 B；原型展示 B 的交互，不代表后台已完成。方案选择后分阶段实现，不一次性替换整个生成系统。

## 3. 图片同步：生成一次、展示两处

1. 用户在任一入口明确提交生成指令，先固定当前 `sessionId`、`messageId`、`runId`、`boardId` 和参考素材快照，再执行。
2. Agent 调用现有生图工具；任务队列创建唯一任务。侧边显示生成状态，画布按现有批量布局预留位置。不从两个UI分别发请求。
3. 图像成功后由现有缓存保存一次，消息卡片只引用结果；画布由统一落位处理器插入。去重键为 `taskId + resultIndex + boardId`，兼容一个任务多个结果。
4. 只有画布元素和画板持久化确认后，聊天卡片才显示“已同步到画布”。点击“定位画布”只是定位，不触发生成或重新插入。
5. 图像生成成功但画布保存失败：保留聊天预览，显示“图片已生成，画布待同步”；“重试同步”只读已有结果，不调用模型。
6. 生成接口失败：显示具体错误和显式“重新生成”，这是新请求。429 不自动重试，不把网络失败伪装成成功。
7. 用户切换画板：结果继续归属提交时的画板；支持的后台保存路径负责落位，否则排队等待该画板可用，不写入新打开的画板。
8. 画布手动删除某张结果后不自动补回。聊天保留历史和预览，并提供明确“重新放到画布”；删除对话也不连带删除画布作品。
9. 续改采用新结果保留原图，避免不可逆覆盖。聊天卡片和画布选中图都可“继续修改”，带入明确的图片引用；多图时先选择目标。

## 4. Agent 对话、流式与思考展示

- 复用 Agent 执行器、现有 MCP 工具/任务队列和文本/图片模型配置。侧栏顶端选文本模型；生图使用现有图片模型配置，生成卡片明确显示实际图片模型，避免把文本模型当生图模型。
- 为 Agent 增加可注入的文本流适配层，复用已实现的协议、凭据桥和取消机制。先审计旧 sendChat 与新协议的接口差异；不能假定每个模型都支持思考字段或工具模式。
- 建议统一事件：`response.delta`、`reasoning.delta`、`tool.started`、`tool.progress`、`tool.completed`、`asset.ready`、`canvas.synced`、`run.failed`、`run.cancelled`。事件带运行身份、序号和事件ID，拒绝重复/过期事件。
- 旧 Agent 的 onChunk 是累计正文，适配成快照或求差量；现有文字流是真正增量的部分直接追加，禁止把累计文本重复拼接。
- 正文直接流式显示。只显示接口实际暴露且允许展示的思考内容/摘要；没有则不渲染思考折叠区。不伪造思考过程，也不把原始系统提示词、工具JSON和普通正文当“思考”。
- 工具执行过程单独用简洁步骤展示：准备参考素材 → 生成图片 → 保存到画布。只有接口有真实进度才给百分比；否则显示阶段和已耗时，不造进度。
- 工具调用须完整解析并通过现有工具白名单及参数校验后执行。流式未完成的文本不能触发任务。首轮开放已核实的图片生成/修改及现有非破坏性画布操作；其余能力维持原边界。
- 普通提问只回复，不因为共享 Agent 就强制生图。明确“生成/改图”的指令可直接执行；仅讨论方案时不隐式调用生图。
- 停止生成：停止当前运行，阻止后续工具，并尝试取消进行中的任务；提供方已接收的任务可能仍返回。后到结果保留在原任务历史、标明“停止后返回”，不自动插入画布；不声称一定停止计费。

## 5. 两个输入框的协同规则

| 用户动作 | 行为 |
| --- | --- |
| 从侧边发送“做一张海报” | 当前会话增加用户消息，Agent执行，图片卡片和当前绑定画板出现同一结果 |
| 底部以Agent模式提交 | 进入当前绑定会话同一执行链；聊天用户消息标注“来自画布”，回复接着已有上下文 |
| 底部以图片模式提交 | 保留精确模型/尺寸/数量参数，直接走现有生图任务；同一会话记录该指令及结果，不额外调用一次文本模型 |
| 点击回复“用作提示词” | 只回填主输入框文字，保留生成类型、图片模型、数量和参考图；已有草稿先确认，不自动发送 |
| 主输入框“与助手讨论” | 把当前提示词及用户勾选的引用加入聊天待发送内容；不消耗请求、不覆盖聊天原草稿 |
| 选中画布图“继续修改” | 打开当前聊天，显示可移除的参考图标签；下一次提交锁定图片引用，避免选区变化后改错图 |
| 聊天卡片“画布参数” | 把对应生成设置放入主输入框，显式确认覆盖；与“仅提示词”回填分开 |
| 切换聊天会话 | 当前画板绑定会话随显式选择变化；后台运行仍属于提交时的会话。已在输入的主草稿不悄悄换归属，提示选择继续原会话或转入新会话 |
| 收起聊天 | 任务与保存继续；主输入框显示当前会话名称和运行状态，可一键回到对应聊天 |

每个画板记住最近明确选择的创作会话，一个会话首轮绑定一个画板。未绑定的旧文本会话仍可纯聊天；第一次生成时选择当前画板或新建画板。打开绑定其他画板的会话时显示目标提示，由用户选择前往；不静默把任务目标改为当前画板。

两个入口草稿独立，但发送后进入同一会话。每会话一次只接受一个Agent运行；另一入口显示运行中，可停止/等待，避免并发续写上下文冲突。不同会话仍可并行，沿用全局任务并发限制。主入口提交或回填有操作ID和锁，双击不会生成两次。

## 6. 关键页面与视觉

| 页面 | 内容和主要交互 |
| --- | --- |
| 画布协同 | 左侧画布、右侧聊天；底部输入框显示当前会话。聊天图片卡片和画布作品一致，可定位、继续修改、回填提示词 |
| Agent执行 | 正文流式输出、可折叠的思考摘要示例、独立工具步骤；画布显示占位。可体验停止、完成及同步 |
| 专注聊天 | 类ChatGPT的信息层级：左侧轻量历史，顶部新建/搜索，单行标题和“…”菜单；中央消息，底部输入，顶部模型与返回画布 |
| 同步待恢复 | 图片已生成，画布未同步；区分重试同步和重新生成；恢复只补齐画布显示 |

历史侧栏约240px，右侧聊天默认约400px且可调整。并排时历史按需浮层展开，避免三列同时挤占画布。统一中性灰白/深灰色调、简洁选中态；保留一键收起、键盘可达和窄窗口重排。多附件时欢迎区让位于消息/输入，不再裁切标题。 思考状态默认采用贴合主输入框顶部的紧凑状态条：宽度与主输入框一致，高度约30px，只保留阶段、简短摘要和打开讨论入口；详细思考与工具步骤放在侧边栏，避免状态条变成第二个对话框。

原型使用本地模拟事件和矢量海报样例，全部按钮只演示本地状态，不访问模型接口，不代表真实生图或原生联调完成。

## 8. 性能与验证

- 执行器独立于React组件；收起面板停止UI订阅与大列表渲染，任务保存继续。更新按会话和任务过滤，不全量重绘画布。
- 保留现有40ms流式渲染/700ms持久化节流作为起点；思考块折叠且按需渲染，长消息与大量历史分批/虚拟化。
- 图片缩略图与原图分离，只加载可见缩略图；引用同一缓存；批量预留位置沿用现有布局，完成不强抢视口。
- 恢复时先核对已有结果/画布元素和链接再补写，避免在“插入成功但标记未写入”的崩溃窗口重复落图。无法确认远端请求结果时标记待核查，不自动重发收费请求。
- 必测：侧边生成一张只产生一个任务、底部发送进入同一会话、累计流不重复、没有reasoning时不出现假思考、普通讨论零生图、双击去重、换画板/换会话归属、收起后台完成、重启恢复、部分多图失败、结果保存失败只重试同步、取消后迟到结果、删除后不自动补回、旧备份兼容。
- 协议与供应商能力分开验收：合成HTTP覆盖四协议；真实模型另获费用额度后逐个验证，不能以接口格式支持宣称所有Claude/OpenAI/DeepSeek型号均可用。
- 性能复用本机长会话和批量图片基线，测输入到下一帧、长任务、挂载节点和内存趋势，不承诺所有硬件零卡顿。
