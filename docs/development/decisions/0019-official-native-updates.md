# ADR-019：正式渠道恢复应用内签名更新

日期：2026-11-06。用户比较自定义安装脚本与原生更新模块后选择 B，批准本地实施。只面向 `tuziapi/tuzi-switch`，不操作测试仓库，不改变账户契约或用户数据。

## 决定

正式 stable 客户端先读取正式 Release 判断是否有新版，再按附件选择更新方式：

1. 有 `latest.json` 或签名附件的版本必须提供完整的签名更新产物。客户端验证各平台附件、地址、状态、大小与摘要元数据，再调用已有 Tauri updater。原生返回版本、当前安装版本和清单内所有平台 URL 必须对应这次正式 Release；不一致则报错并释放资源。
2. 只有没有声明签名更新的历史版本才走原有手动下载兼容入口。网络、签名、缺包或清单错误不得触发未签名安装兜底，也不能误报“已是最新”。
3. 提醒与设置入口先展示说明。用户点击下载后在应用内下载并由原生校验字节签名；用户再次点击“重启并更新”才执行现有创作保存屏障、原生任务检查、安装及重启。未完成任务或保存失败阻止安装；下载/校验/安装错误可明确重试。
4. 保留正式公钥与现有 Secret，不新生成、不替换、不复制测试私钥。移除默认配置里的陈旧 raw/CDN 清单地址；正式打包配置原本已只使用正式 Release endpoint。
5. 用正式仓库的受限预检工作流签署合成探针并验证现有公钥。Secret 名称存在不代表配对验证成功。预检只读取源码、验证签名，不构建、不上传附件、不发布。正式原生发行仍使用已有完整签名流水线。

这覆盖 ADR-018 中正式渠道始终选择手动安装的运行时决策，同时保留未签名历史版本的可见性。

## 选择依据

| 方案 | 优点 | 成本与限制 |
| --- | --- | --- |
| 自定义更新脚本 | 可针对已有手动安装包编排 | 自行维护三平台权限、退出、替换及恢复；没有现成签名安装链 |
| 原生更新模块（用户选择） | 复用下载进度、验签、保存屏障与安装重启 | 必须有匹配的私钥、完整签名附件及真实安装验收；安装权限/系统行为仍受平台限制 |

直接只读签名清单会重复此前“陈旧清单隐藏新版”的问题，所以保留 Release 发现，再验证签名清单与发行版本一致。缺少完整签名发布时不冒充具备应用内安装能力。

## 兼容、回退和新增字段

- 最初 v1.5.5 走签名清单；若旧公钥对应私钥可用，后续签名发行有机会恢复旧路径，仍需实际旧包验证，不能只凭配置确认成功。
- 后来手动检测版 v1.5.5 / v1.5.6 已写死手动下载，需要先安装一次包含本实现的过渡版；修改服务器清单无法改变其二进制逻辑。
- 新版到再下一版必须完成真实安装升级及数据保留验收。测试中的 1.5.7 是合成版本，不代表已发布或已决定下一版本号。
- 仅新增 CI 布尔输入 `signing_preflight_only`，默认 `false`；为 `true` 时只允许正式签名预检，常规 verify/installers/assemble/publish 不执行。应用、账户、数据库无新增持久化字段。
- 回退本提交可恢复手动检测行为，不删除用户数据、不撤销已发布附件、不旋转密钥。正式签名不能替代开发者签名、公证或跨平台实机验收。

实施证据、授权边界及发布前验收清单见 [OFFICIAL-UP-02](../2026-11-06-official-native-updates.md)。

## 2026-11-11：手动入口固定版本

用户报告 Windows 手动下载立即失败后，修复已经判定为手动交付的分支：在检查阶段完成来源/版本/附件校验并固定 URL，点击只请求浏览器打开该版本。移除点击时的重复 latest 查询，避免网络和新版出现阻断既有有效链接；撤回附件由 GitHub 返回不可用，客户端不会自行切换版本。此动作仅打开浏览器，不执行安装或声称下载字节已验证。签名声明与错误不转为手动 handle，签名自动安装原约束不变。见 [修复记录](../2026-11-11-update-download-recovery.md)。
