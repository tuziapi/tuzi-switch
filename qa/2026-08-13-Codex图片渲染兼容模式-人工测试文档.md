# 2026-08-13 Codex 图片渲染兼容模式人工测试文档

> 实现说明：[Codex 图片渲染兼容模式交接文档](../docs/2026-08-13-Codex图片渲染兼容模式-交接文档.md)

## 验收范围

本轮验收覆盖：

- “Codex 图片渲染兼容模式”默认值、设置页和只读状态。
- Tuzi `/v1`、`/coding` Provider 识别与 Key 私密派生。
- 8 条 Images API 路由。
- `gpt-image-2` generation 和 edit 请求。
- 原始请求保留、临时文件流式上传和响应流式转发。
- 请求大小、超时、multipart、并发和浏览器来源限制。
- 单次 POST、禁止自动重定向和自动重试。
- 受管 Skill、个性化区块和空白图片渲染兜底。
- 接管 ownership、手动关闭抑制和 Provider 热切换。
- Codex 配置目录切换、同步下载和失败回滚。
- CC Switch 隔离。

## 强制隔离要求

人工测试必须遵守：

1. 只运行当前 Tuzi Switch 工作区构建。
2. 不启动、不修改、不覆盖 CC Switch。
3. 不使用已安装的其他桌面版本判断当前工作区功能。
4. 推荐把 Codex 配置目录指向专用测试目录，不直接测试真实 `~/.codex`。
5. 使用测试 API Key；截图和日志不得包含 Key 明文。
6. 测试前备份测试目录和 Tuzi Switch 测试数据库。
7. 真实 generation/edit 会调用上游并可能计费，执行前必须确认。

### QA-02 设置页展示实际配置

步骤：

1. 选择 Provider A。
2. 填入测试 Key 并保存。
3. 打开图片兼容详情。

预期：

- Provider URL 显示 `https://api.tu-zi.com/v1`，标记“保持不变”。
- Provider `env_key` 显示 `TUZI_CODEX_API_KEY`，标记“保持不变”。
- 图片上游显示 `https://api.tu-zi.com/coding`。
- 图片模型显示 `gpt-image-2`。
- 私密派生 Key 只显示名称 `TUZI_CODEX_IMAGE_API_KEY`。
- 页面中没有 API Key 明文。

### QA-03 未就绪原因

分别制造：

- 未选择 Provider
- Provider C
- 无效 TOML

## Provider 与 Key 验收

### QA-04 `/v1` 保持不变但图片内部走 `/coding`

步骤：

1. 选择 Provider A。
2. 记录 Provider 表单和数据库中的配置。
3. 开启兼容模式并完成一次 generation。
4. 再次查看 Provider。

预期：

- Provider 原始 `base_url` 仍是 `/v1`。
- Provider `env_key` 未变化。
- 图片请求实际进入 `/coding/images/generations`。
- 关闭接管后 live 配置恢复 Provider 原配置。

### QA-05 `/coding` Provider

步骤：

1. 切换到 Provider B。
2. 确认兼容状态重新就绪。
3. 执行一次 generation。

预期：

- 派生 Key 更新为 Provider B 的 Key。
- 不继续使用 Provider A 的旧 Key。
- Provider B 配置未被改成其他 URL 或 `env_key`。

### QA-06 任意 `env_key` 读取防护

步骤：

1. 创建 Tuzi `/v1` Provider，但把 `env_key` 写成
   `AWS_SECRET_ACCESS_KEY`。
2. 确保测试进程环境中该变量非空。
3. 保存并读取图片兼容状态。

预期：

- 不把该变量派生到 `TUZI_CODEX_IMAGE_API_KEY`。
- 状态为缺少凭据或配置不可用。
- 日志、页面和受管文件均不出现该变量的值。

### QA-07 系统环境变量不被修改

步骤：

1. 记录进程启动前的 `TUZI_CODEX_IMAGE_API_KEY`。
2. 切换 Provider A / B。
3. 读取子进程或测试进程环境。

预期：

- 兼容层只更新 Tuzi Switch 受管文件。
- 不调用系统环境变量持久化。
- 用户原有同名进程变量不被覆盖。

## 接管状态机验收

### QA-08 自动接管

步骤：

1. 图片兼容开启。
2. 选择有有效 Key 的 Provider A。
3. 确保 Codex 尚未接管。

预期：

- 兼容文件就绪后自动开启 Codex 本地路由。
- live 地址指向当前本地代理。
- live 配置含当前进程 `x-tuzi-image-token`。

### QA-09 手动关闭后不自动夺回

步骤：

1. 等待 QA-08 就绪。
2. 用户手动关闭 Codex 接管。
3. 在 Provider A 与 B 之间切换。
4. 保存或刷新 Provider。

预期：

- Codex 接管保持关闭。
- Provider 变更不会自动重新开启。
- ownership 状态为 `manual_disabled`。

### QA-10 关闭再开启兼容模式

步骤：

1. 处于 QA-09 的手动抑制状态。
2. 关闭图片兼容模式。
3. 再次开启。

预期：

- 关闭时清除抑制状态并卸载属于 Tuzi Switch 的受管内容。
- 再次开启且条件满足时允许自动接管。

### QA-11 手动开启转移 ownership

步骤：

1. 用户手动开启 Codex 接管。
2. 随后关闭图片兼容模式。

预期：

- 用户主动开启的接管不被图片兼容当成自己拥有。
- 关闭图片兼容只清理图片受管内容，不擅自关闭用户接管。

### QA-12 接管中的 Provider 热切换

步骤：

1. 图片兼容处于自动接管状态。
2. 在 Provider A 与 B 之间切换。
3. 分别确认受管 Key、当前代理目标和 live 恢复备份。

预期：

- 先更新受管 Key，切换瞬间不继续使用旧 Provider 的 Key。
- 当前代理目标和 live 恢复备份更新为新 Provider。
- 接管保持开启，ownership 不变，不写入 `manual_disabled`。

## Images API 验收

### QA-13 generation

步骤：

1. 使用有效测试 Key。
2. 在 Codex 中要求生成一张低成本测试图片。
3. 观察本地路由和上游结果。

预期：

- 使用 `gpt-image-2`。
- 请求命中 generation Images API。
- prompt、尺寸、数量等原始字段不被文本模型逻辑改写。
- 响应以流式方式返回。
- 日志中不出现完整 Base64。

### QA-14 generation 非法请求

分别测试：

- 非 JSON Content-Type
- 非 `gpt-image-2`
- 声明或实际超过 4 MiB
- 上传长时间无数据

预期：

- 请求在本地被拒绝。
- 不提交到上游。
- 不占用无限期并发槽。

### QA-15 edit

步骤：

1. 准备一张小型测试 PNG。
2. 执行图片编辑请求。
3. 对比发送前后的 multipart 原始字节。

预期：

- 请求命中 edit Images API。
- multipart 不重建。
- 原始图片二进制保持一致。
- 请求流式写入临时文件，再流式发送。
- 请求结束、失败或取消后临时文件被回收。

### QA-16 edit 防护

分别测试：

- 缺少 model
- model 不是 `gpt-image-2`
- 重复 model
- 空或超长 boundary
- 超长 multipart header
- 超过 64 个字段
- 超过 64 MiB
- 压缩 edit 请求
- 上传空闲超时

预期：

- 全部在本地拒绝。
- 不把完整请求载入内存。
- 不遗留长期临时文件。

### QA-17 并发限制

步骤：

1. 同时占用 4 个图片请求槽。
2. 发起第 5 个请求。

预期：

- 第 5 个请求返回 `429`。
- 响应包含 `Retry-After: 1`。
- 前 4 个请求结束后可再次提交。

### QA-18 单次提交

步骤：

1. 使用测试上游分别返回 `307` 和 `308`。
2. 记录上游收到的 POST 次数。

预期：

- 客户端收到 3xx。
- 上游只收到 1 次 POST。
- 不访问重定向 Location。

再分别模拟超时、连接中断、429、5xx：

- 当前请求不自动换 Key 或 Provider 重放。
- 不宣称同请求透明故障转移。

## 本地安全验收

### QA-19 来源与凭据

分别发送：

- 非 loopback TCP 请求
- 缺少 `Bearer PROXY_MANAGED`
- 缺少或使用旧 `x-tuzi-image-token`
- 带 `Origin`
- 带 `Sec-Fetch-Site`

预期：

- 全部返回认证错误。
- 不向图片上游发送请求。

### QA-20 监听地址

分别配置：

- `127.0.0.1`
- `::1`
- `0.0.0.0`
- `::`
- 一个 LAN 地址

预期：

- 前四种可通过回环地址形成图片路由。
- LAN 地址不报告 ready，不自动开启图片接管。

### QA-21 文件权限

Unix 下检查：

```bash
stat -f "%Lp %N" <测试 Codex config.toml>
stat -f "%Lp %N" <测试 Tuzi Switch codex-env>
```

预期：权限为 `600`。

Windows 下检查：

- 文件位于测试用户目录。
- 不创建全局共享明文 Key 文件。

### QA-23 原生图片卡片空白

## 发布阻断条件

出现以下任一情况不得发布：

- Provider 原始 `/v1` 或 `env_key` 被兼容层永久改写。
- API Key 明文出现在设置页、普通日志或图片 Base64 日志中。
- 非 loopback 或浏览器来源可以访问 Images API。
- 图片请求发生自动重放。
- edit 请求被完整载入内存，或临时文件长期残留。
- 用户手动关闭接管后被自动重新开启。
- 关闭图片兼容误关用户主动开启的接管。
- Codex 目录切换失败后未恢复旧状态。
- 覆盖或删除不属于 Tuzi Switch 的 Skill / AGENTS 内容。
- 启动、修改或覆盖 CC Switch。
