# API 配置生效与 Codex 供应商落盘人工测试文档

## 测试环境

- 兔子switch：1.1.29 待验证构建
- Codex CLI：0.134.0 或更新
- Claude Code：新版 `~/.claude/settings.json` 配置路径

## 测试用例

### 1. Claude API 配置保存后生效

1. 在兔子switch 中编辑当前 Claude 供应商，修改 API Key 或 base URL。
2. 保存后退出并重启 Claude Code。
3. 检查 `~/.claude/settings.json` 中的 `env` 已更新。
4. 发起 Claude 请求，确认走新配置。

预期：不再写入旧 `~/.claude/claude.json`，Claude 重启后读取新配置。

### 2. Codex 新增供应商不切换当前配置

1. 准备已有 `~/.codex/config.toml`，顶层 `model_provider` 指向旧 provider。
2. 在兔子switch 中新增一个 Codex 预设供应商，保存但不点击启用。
3. 检查 `~/.codex/config.toml`。
4. 检查 `~/.codex/<供应商名>.config.toml`。

预期：

- 顶层 `model_provider` 仍是旧 provider。
- 主配置新增目标 `[model_providers.*]`。
- 新 profile 文件存在，内容包含目标 provider 配置。
- 既有 MCP/project 配置未丢失。

### 3. Codex 多兔子线路不覆盖用户已有 tuzi

1. 准备已有 `~/.codex/config.toml`，其中包含 `[model_providers.tuzi]` 和 `env_key = "TUZI_CODEX_API_KEY"`。
2. 在兔子switch 中新增 Codex “兔子线路”供应商并保存。
3. 检查新增供应商的配置和 `~/.codex/config.toml`。

预期：

- 原 `[model_providers.tuzi]` 仍保留，内容未被新供应商覆盖。
- 新供应商使用 `provider-tuzi01` 或下一个可用编号，如 `provider-tuzi02`。
- env key 与编号一致，如 `TUZI01_CODEX_API_KEY` 或 `TUZI02_CODEX_API_KEY`。
- 如果已有 `provider-tuzi01`，再次新增应生成 `provider-tuzi02`。

### 4. Codex 保存入口不双跳编号

1. 准备已有 `[model_providers.tuzi]` 和一个已存在的 `provider-tuzi01` 供应商。
2. 在 Codex 供应商表单中保存一个旧格式 `model_provider = "tuzi"` 的兔子线路配置。
3. 检查 `~/.codex/config.toml` 和兔子switch 中该供应商的配置。

预期：

- live 配置新增 `provider-tuzi02`。
- 供应商入库配置同样是 `provider-tuzi02`。
- 不应出现 live 是 `provider-tuzi02`、数据库供应商变成 `provider-tuzi03` 的双跳号问题。

### 5. Codex 首次导入已有配置

1. 在安装/启动前准备已有 `~/.codex/config.toml`。
2. 启动兔子switch。
3. 打开 Codex 供应商列表。

预期：

- 官方预设仍存在：`兔子线路`、`codex订阅`、`gaccode`。
- 额外出现 `当前 Codex 配置`，内部 id 为 `codex-live-config`。
- 若原配置使用 `tuzi`，导入后的供应商改用 `provider-tuziNN`，不覆盖原 `tuzi`。
- 重启兔子switch 后不会重复生成第二个 `当前 Codex 配置`。

### 6. Codex 切换供应商

1. 在 Codex 供应商列表点击新供应商“启用”。
2. 检查 `~/.codex/config.toml` 顶层 `model_provider`。
3. 启动 Codex 发起请求。

预期：顶层 `model_provider` 指向新供应商，不会被改回旧 provider id。

### 7. Codex 预设命名与重复校验

1. 新增 Codex 供应商并选择预设。
2. 检查默认名称。
3. 手动改成已存在供应商名称并保存。

预期：

- 默认名称为 `供应商名-我的配置`。
- 名称重复时表单提示重复，不提交。

### 8. 更新安装后的重启提示

1. 在关于页检查并下载安装更新。
2. 等待安装完成。
3. 观察弹窗。

预期：安装完成后出现重启确认弹窗；点击“立即重启”才重启，点击“稍后重启”保持运行。

### 9. 删除供应商不改真实配置

1. 准备任意应用的两个供应商，当前使用 A，待删除 B。
2. 对 Codex，确认 `~/.codex/config.toml` 中包含 B 的 `[model_providers.<route>]`，且 `~/.codex/<B供应商名>.config.toml` 存在。
3. 对 OpenCode/OpenClaw/Hermes，确认对应客户端配置文件中包含 B。
4. 点击 B 卡片的删除按钮并确认删除。
5. 检查兔子switch 列表、对应真实客户端配置文件和 env。

预期：

- B 从兔子switch 列表消失。
- 真实客户端配置文件中的 B 保留。
- B 的 profile/env key 保留。
- A 的配置保留。
- 如需从真实客户端配置移除 B，应使用独立的“移除配置”动作，而不是卡片删除。

### 10. 移除配置仍可改真实配置

1. 准备 OpenCode/OpenClaw/Hermes 等累加模式供应商 B，并确保 B 已存在于对应客户端配置文件。
2. 点击 B 的“移除配置”动作，而不是删除卡片。
3. 检查兔子switch 列表和对应客户端配置文件。

预期：

- B 仍保留在兔子switch 列表。
- B 从真实客户端配置文件中移除。
- 这与卡片删除形成明确区别。

### 11. 当前供应商删除入口提示

1. 打开任意普通模式供应商列表，如 Codex。
2. 查看当前使用中的供应商卡片右侧操作区。
3. 悬停删除按钮。
4. 切换到其他供应商后再查看原供应商删除按钮。

预期：

- 操作按钮不依赖悬停才出现。
- 当前使用中的供应商删除按钮禁用，并提示先启用其他供应商。
- 非当前供应商删除按钮可点击，并弹出删除确认。
