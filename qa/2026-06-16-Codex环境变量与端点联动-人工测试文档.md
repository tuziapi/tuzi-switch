# Codex 环境变量与端点联动人工测试文档

## 测试环境

- 兔子switch：1.1.30 待验证构建
- Codex CLI：0.134.0 或更新
- macOS shell：zsh
- Linux shell：zsh、bash、其他 shell 各测一次
- Windows：用户环境变量

## 测试准备

为避免污染真实配置，人工测试建议先备份：

- `~/.codex/config.toml`
- `~/.zshrc`
- Linux 对应 rc 文件，如 `~/.bashrc`、`~/.profile`

测试完成后按备份恢复。Windows 测试前记录已有用户环境变量。

## 测试用例

### 1. 新增 Codex 供应商可填写环境变量名

1. 打开 Codex 供应商新增表单。
2. 选择任意 Codex 预设。
3. 在“环境变量名”输入 `MY_CODEX_API_KEY`。
4. 填写 API Key 和 API 请求地址。
5. 保存。

预期：

- 表单保存成功。
- `~/.codex/config.toml` 对应 provider 的 `env_key` 为 `MY_CODEX_API_KEY`。
- 兔子switch DB 中保存的配置与 `config.toml` 一致。

### 2. 环境变量名格式限制

1. 在环境变量名输入框尝试输入 `MY-CODEX KEY!`。
2. 保存。

预期：

- 输入框只保留字母、数字、下划线。
- 若仍存在非法值，保存时提示只能使用字母、数字、下划线。
- 不写入 Codex 配置和环境变量文件。

### 3. 环境变量名重复拦截

1. 准备两个 Codex provider。
2. 将第二个 provider 的环境变量名改成第一个 provider 已使用的值。
3. 保存。

预期：

- 保存被阻止。
- UI 提示环境变量名重复。
- 原 `~/.codex/config.toml` 不被覆盖。

### 4. 兔子线路编号不覆盖已有变量

1. 准备已有 Codex 配置，包含 `env_key = "TUZI_CODEX_API_KEY"`。
2. 新增 Codex “兔子线路”供应商。
3. 保存。

预期：

- 新供应商使用 `TUZI01_CODEX_API_KEY`。
- 已有 `TUZI_CODEX_API_KEY` 不被覆盖。
- 再新增一次时使用 `TUZI02_CODEX_API_KEY` 或下一个未占用编号。

### 5. API 请求地址联动配置预览

1. 打开 Codex 供应商新增或编辑表单。
2. 在 API 请求地址选择/输入区域切换到另一个 endpoint。
3. 观察下方 Codex TOML 配置预览。
4. 保存后检查 `~/.codex/config.toml`。

预期：

- 配置预览里的 active provider `base_url` 立即跟随变化。
- 保存后的 `base_url` 与表单 API 请求地址一致。

### 6. macOS 写入 `~/.zshrc`

1. 在 `~/.zshrc` 中准备 `# Codex` 分组。
2. 新增 Codex provider，环境变量名填写 `MAC_CODEX_API_KEY`。
3. 保存。
4. 检查 `~/.zshrc`。

预期：

- `export MAC_CODEX_API_KEY=...` 写入 `# Codex` 分组下。
- 不重复追加同名变量。
- 没有 `# Codex` 分组时，写入 tuzi-switch managed block。

### 7. Linux 写入真实 shell rc 文件

1. 在 Linux zsh 环境测试一次，保存 `LINUX_ZSH_CODEX_API_KEY`。
2. 在 Linux bash 环境测试一次，保存 `LINUX_BASH_CODEX_API_KEY`。
3. 在其他 shell 环境测试一次，保存 `LINUX_PROFILE_CODEX_API_KEY`。

预期：

- zsh 写入 `~/.zshrc`。
- bash 写入 `~/.bashrc`。
- 其他 shell 写入 `~/.profile`。
- 只写当前 shell 对应文件，不因为其他文件有 `# Codex` 就误写。

### 8. Windows 写入用户环境变量

1. 在 Windows 新增 Codex provider。
2. 环境变量名填写 `WIN_CODEX_API_KEY`。
3. 保存。
4. 打开“高级系统设置 > 环境变量”。

预期：

- 用户环境变量中出现 `WIN_CODEX_API_KEY`。
- 不创建 shell rc 文本文件。
- 重启 Codex 或终端后能读取新变量。

### 9. 删除供应商不删除真实配置

1. 新增一个 Codex provider 并保存 API Key。
2. 确认 `~/.codex/config.toml` 和环境变量文件中都有对应配置。
3. 在兔子switch 删除该 provider 卡片。
4. 再次检查配置文件和环境变量文件。

预期：

- 兔子switch 列表中该 provider 消失。
- `~/.codex/config.toml` 中的 provider 配置保留。
- 环境变量文件中的 key 保留。

### 10. 发布后更新链路冒烟

1. 使用 1.1.29 安装版检查更新。
2. 检测到 1.1.30 后点击下载更新。
3. 等待更新下载完成。
4. 观察顶部更新入口和关于页更新弹窗。

预期：

- 顶部出现更新按钮和弹窗入口。
- 下载进度正常变化。
- 安装完成后弹出重启确认。
- 用户点击重启后升级到 1.1.30。
